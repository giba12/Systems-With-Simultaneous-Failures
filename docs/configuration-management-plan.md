Configuration management here is **git plus a CI workflow plus a generated traceability matrix**. This plan writes down what
is already practised, says what is not, and lists the gaps.

## 1. General product definition and scope

**Product.** The Space System Reliability Analyzer: C++20 library `reliability`, command-line tool `analyze`, Python
experiment layer, tests, documents. The analysed satellite system is fictional.

**Scope of CM.** Everything tracked in git, the build and test configuration, the third-party dependencies pulled at
configure time, and the published evidence (verification, experiment and traceability records). Out of scope: any flight or
customer baseline (there is none) and subcontractors (there are none).

## 2. Description of CM activities and procedures

### 2.1 Configuration identification
- **Version.** The product version is `project(... VERSION 0.8.0)` in `project/CMakeLists.txt`; it is compiled into the tool and printed as `tool.version` in every result and recorded in every experiment result (a run that mixes versions is refused).
- **Revision.** The git commit hash. Reports quote hashes (for example run 40394591079 at `88d62f2`).
- **Naming.** Requirements `SYS|ALG|REL|VER|EXP|DOC|INT|NFR-nnn`; test cases `TC-x-nn`; oracles `ORC-n`; user stories `US-nn`; use cases `UC-n`; deviations `A1…E…`; decisions `ADR-nnnn`; gates `G1…G7`.
- **Tags.** None exist yet (see §8).

### 2.3 Change control
1. One maintainer commits directly to `main` (all 28 commits are by the same author). There is no review step, no required pull request, no branch protection.
2. Every push and pull request triggers CI (`ci.yml`): g++ and clang++ in Release and g++ with ASan/UBSan in Debug, each running all 129 `ctest` entries, which include the Python end-to-end tests and the traceability check.
3. A change that adds or removes a requirement or a test case must keep `check_traceability.py` clean; the generated matrix is regenerated with `--write`.
4. **Hypothesis-first rule.** A new experiment starts with a commit that contains only its hypothesis file; the runner refuses to run without one and records its SHA-256 (ADR-0006).
5. **Records of measurements are dated and not rewritten** when the code changes later (commit `b662153` left them as they were); stale statements are fixed in follow-up commits.
6. A deviation from the paper or the guide is entered in the [deviation log](deviation-log.md); a design decision in the [decision log](decision-log.md), in the same commit as the change.
7. Commit messages state what changed and what was run (test counts, compilers). A commit that only records a CI run for the preceding commit is made separately (for example `d5c99fc`, `c7cc43d`).

### 2.4 Configuration status accounting
- `git log` is the change history (28 commits, 2026-10-21 – 2026-10-27).
- [traceability-matrix.md](traceability-matrix.md) is the generated status of requirements → test cases → test code.
- [verification-report.md](verification-report.md) §2 and §6 record, per configuration, the compiler, build type, number of tests passed and the CI run id.
- [deviation-log.md](deviation-log.md) and [decision-log.md](decision-log.md) record departures and decisions.
- The README's "Honest status" section records what is not yet true.

### 2.5 Configuration audits

| Audit | How | When |
|---|---|---|
| Traceability | `python3 project/tools/check_traceability.py` (CTest test `traceability`) | every CI run |
| Build and test | `cmake`, `cmake --build`, `ctest` on two compilers and under sanitizers | every push |
| Fresh-copy check (gate G7) | a copy without ignored files is configured, built, tested; `demo.sh`, the analyses, the experiments, the venv, the analysis and the plots are run from the README | 2026-10-22; repeated after the repair-policy extension; **not automated** |
| Reproducibility | the deterministic experiment result files are byte-identical on repeat | on demand (TC-G-01) |
| Documentation consistency | review (TC-H-03); the commit `b662153` fixed stale comments and counts found this way | on demand |

### 2.6 Build and release
- Build: `cmake -S project -B project/build -DCMAKE_BUILD_TYPE=Release && cmake --build project/build --parallel`; default build type Release; strict warnings (`-Wall -Wextra -Wpedantic`); no warnings tolerated.
- Release: there are no releases. The version description ([version-description.md](version-description.md)) describes 0.8.0 as a candidate release, and §8 lists what is needed to make it one.
- Dependencies: pinned by version (GoogleTest 1.14.0, nlohmann/json 3.11.3, `ubuntu-24.04`, `actions/checkout@v7`, `actions/setup-python@v7`, Python 3.12 in CI); **not** pinned by checksum. The Python packages in `requirements.txt` (`numpy`, `pandas`, `matplotlib`) are **not** version-pinned; the versions used are recorded in the verification report (numpy 2.5.4, pandas 3.0.6, matplotlib 3.11.2).
